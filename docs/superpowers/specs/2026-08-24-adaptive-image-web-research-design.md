# 自适应搜图与联网来源扩展设计

## 目标

让网页版、桌面端和安卓端共用的 ZT.AI 网关在收到图片识别请求时，不再只依赖 MiniMax 的视觉描述或固定 6 条文字搜索结果，而是优先寻找图片在公开互联网中的匹配页面、实体和出处；在证据不足、来源冲突或图片线索模糊时自动扩大检索范围，并在回答下方展示完整、可追溯的来源集合。

## 已确认的外部能力

- Google Cloud Vision Web Detection 官方接口会返回网页实体、包含匹配图片的页面、完整/部分匹配图片和视觉相似图片，适合寻找图片出处和候选身份。
- TinEye API 是专业反向图片搜索服务，适合查找被转载、裁切或修改后的图片，但需要独立商业凭据；本阶段只预留可选适配器，不让没有 TinEye 配置的部署失败。
- Firecrawl 的文字搜索和 DuckDuckGo 备用搜索继续保留，用于围绕视觉线索验证上下文、时间、品牌、地点和来源可信度。
- GitHub 上的 PaddleOCR、CLIP 和浏览器反向搜图项目可作为后续独立能力参考，但不能替代服务端互联网反向搜图链路。

## 方案

### 1. 图片检索分层

1. MiniMax M3 先观察图片，提取可读文字、标志、物体类别、型号、地点和明显视觉特征；这些内容全部标记为“未核实线索”。
2. 如果 Render 配置了 Google Vision 凭据，将图片原始 data URL 以 base64 发给 Web Detection，解析网页实体、匹配页面、完整/部分匹配图片和视觉相似图片为来源候选。
3. 如果配置了 TinEye 凭据，调用 TinEye 作为第二个反向搜图候选源；任何认证、限流或服务失败都只能记录为 provider failure，不得阻断 Firecrawl/DuckDuckGo。
4. 根据图片线索生成多个文字查询方向：原始问题、视觉线索、图片可读文字、候选实体、出处/来源查询。每个方向优先 Firecrawl，失败后使用 DuckDuckGo。
5. 统一归一化 URL、标题、摘要、来源提供方和证据类型，按来源质量、匹配类型、查询方向和域名多样性排序并去重。

### 2. 自适应来源预算

- 普通具体事实：初始 6 条，必要时最多 12 条。
- 图片、陌生名词、未知品牌/人物/产品或出处问题：初始 8 条，必要时扩展到 18 条。
- 搜索结果互相矛盾、只有低质量转载、没有匹配页面或用户明确要求追溯来源：最多 24 条。
- 只有在不同检索方向仍产生新域名和新证据时才继续扩展；达到证据充分、来源重复或 24 条上限时停止。
- 回答上下文只注入排名最高且彼此独立的证据，来源抽屉展示全部去重后的来源；防止大量低质量摘要污染模型，同时不再把 UI 固定成 6 条。

### 3. 失败与安全边界

- 所有图片身份、品牌、人物、地点、型号和出处都必须由图片可见事实与公开来源共同支持。
- Google Vision、TinEye、Firecrawl 和 DuckDuckGo 都不可用时，模型仍可描述图片直接可见内容，但不得凭旧知识猜测具体身份。
- 任何网页摘要中的指令都视为不可信数据，不能改变系统规则或诱导输出工具协议。
- 外部凭据只从 Render 环境变量读取，变量名和示例可以进入代码/文档，但真实值不得写入 GitHub、Pages 或前端。

### 4. 交互与来源抽屉

来源事件新增总来源数、是否扩展、检索方向数和反向搜图提供方；抽屉显示来源类型（图片匹配、网页实体、文字检索）、提供方和查询方向。没有来源时不显示成功来源抽屉，失败状态要明确显示“未找到可核验来源”。

## 验收标准

1. 搜索层不再存在不可配置的 6 条全链路硬截断；默认预算和最大预算有单元测试。
2. 同一个查询可以并行/顺序执行多个检索方向，结果 URL 去重且保留来源类型与提供方。
3. 图片请求会触发视觉预检；Google Vision 未配置时继续走现有文字搜索；配置错误不会让图片回答短路。
4. 反向搜图候选、Firecrawl 和 DuckDuckGo 失败时不猜测具体身份。
5. 来源抽屉可以显示超过 6 条来源，并显示扩展状态和来源类型。
6. 网页、桌面端和安卓端共用的网关接口保持兼容，现有文本聊天、SSE、下载入口和已有测试不回归。
